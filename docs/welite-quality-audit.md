# WeLite 功能与同步验收

目标：解决现有功能问题，重点验证双向同步；清理不必要实现与重复职责；在 KOReader 模拟器验证全部功能。测试通过不等于目标完成。

新增明确范围：接入 WeRead 的公众号、章节预下载、书评、划线和想法、书籍搜索；结合现有 WeLite UI，功能正常且风格一致。仅有上游 API 或隐藏菜单不算完成。

## 必须保留的交互

- 主页同步刷新书架、云端阅读进度和阅读时间；不自动打开书籍。
- 打开对应书籍后再比较进度、选择本地或云端。
- 复用 WeRead 客户端、位置映射、报告上传及宿主阅读能力。修复行为必须有回归证据，不另建平行协议栈。
- 同步状态必须区分数据刷新、待选择、上传失败和已确认完成。
- 明确取消不会上传、跳页或误报完成；账号切换与文档关闭使旧回调失效。

- 所有位置上传复用账本中现有的按配置目录/账号/书籍区分的进程内 reservation 表。rt=0 的进度写入只占用内存锁，不创建虚假的时长批次或 SQLite 时间记录；它与主页补报、定时报告相互排斥，其他书和账号不受影响。启动失败释放锁，旧 token 不会释放新请求的锁。
- 取消请求后，进度锁与正时长批次均保留到子进程实际退出/回收；此时才释放位置锁或将未确认时长转为 uncertain。正常收到结果则立即释放，再由原有流程校验账号、保存结果和调用完成回调。宿主 terminateSubProcess 使用 SIGKILL；不新增轮询任务，复用原有回收器和有上限的进度 busy 重试。
- 新增真实 SQLite/子进程用例：20 秒主页批次在途时开书，15 秒新阅读正常积累；批次完成后再读 5 秒，实际只上报本次的 20 秒，总确认 40 秒。关书保留 5 秒，再发送 rt=0 的进度，此时主页不能抢占同书；进度完成后可补报余下 5 秒，总计 45 秒，无 uncertain、无重复。另覆盖启动抛错和取消后的延迟退出（零时长/正时长两种写入）。
- 此修复串行化同一 KOReader 进程内的写入，并不提供服务端原子比较更新；其他物理设备同时更新的竞争仍不能据此宣称已解决。

验证结果：完整 `make test` 通过 175 项 KOReader 原生测试、89 组 Lua 规格和 7 项 Python 测试（`/tmp/welite-concurrent-reading-time.log`）。随后完善正时长取消时的延迟释放，对受影响的时长账本和完整进度同步流程重跑 30 项原生测试，全部通过（`.dev/reports/concurrent-time-sync.xml`，80.77 秒）；最终 89 组 Lua 规格再次全部通过。`make check`、`make package`、`git diff --check` 通过。此轮使用桌面模拟器和合成服务响应，没有真实账号写入。

### 多账本实例之间的落盘失败恢复

- 用独立存储句柄复现数据丢失：阅读器 checkpoint 写盘失败后，主页句柄看不到这 10 秒待保存时长；反向保存时旧阅读器实例又会覆盖主页新增记录。修复前规格实际失败于 `another handle lost the failed checkpoint`，日志 `/tmp/welite-shared-ledger-before.log`。
- 将每实例 failed_state 改为按 storage_id（无路径时按存储对象）共享的 dirty_states。只在有保存失败时保留一份既有上限 256 条记录的状态，成功落盘立即移除；各实例后续操作都基于最新待保存状态，避免旧副本覆盖。未增加依赖、网络请求、自动重试循环或额外文件。
- recover 会重试尚未落盘的状态，即使没有孤立批次需要转换；重复回执也会先完成未成功的保存。服务器请求完成后释放网络 reservation，但下一次时长领取必须成功保存，下一次进度写入也先通过 recover 保存检查；磁盘仍不可写时不会绕过失败继续发送。
- 原生用例用真实 SQLite BEGIN IMMEDIATE 写锁制造失败，随后恢复：两个句柄分别产生的 15 秒/5 秒均落盘；19 秒已确认回执保存失败后仍能恢复，另一个账号新增 3 秒也保留，独立只读 SQLite 查询验证最终数据。回执重复处理不增加秒数。主页对本地记录错误显示原始原因（最多 300 字符），不只显示笼统同步失败。
